# TechFlowトラブルシューティングガイド

## APIが429（レート制限）を返す

### 症状
APIリクエストが「Rate limit exceeded. Retry after 30 seconds.」のようなメッセージとともにHTTP 429を返します。これは、アプリケーションがプランティアで許可されたリクエストレートを超えた場合に発生します。

### 診断
1. APIレスポンスの`X-RateLimit-Remaining`ヘッダーを確認してください。常に0であれば、制限に達しています。
2. リクエストパターンを見直してください——不要なポーリング呼び出しをしていませんか？失敗したリクエストを過度に積極的にリトライしていませんか？
3. 複数のサービスやアプリケーションが同じAPIキーを共有していないか確認してください。

### 解決策
- **指数バックオフを実装する**: 429を受け取ったら、`Retry-After`ヘッダーに示された秒数待機し、以降のリトライごとに待機時間を2倍にする（最大5回リトライ）。
- **APIレスポンスをキャッシュする**: 同じデータを繰り返し取得している場合、30〜60秒ローカルにキャッシュしてください。
- **ポーリングの代わりにWebhookを使う**: `GET /v3/tasks`を10秒ごとにポーリングする代わりに、`task.updated`イベント用のWebhookを登録してください。
- **レート制限の引き上げをリクエストする**: ProおよびEnterpriseプランは、support@techflow.comに連絡することでカスタムのレート制限をリクエストできます。
- **バルクエンドポイントを使う**: タスクを1件ずつ取得する代わりに、`GET /v3/projects/{id}/tasks?limit=100`でリクエストをまとめてください。

## Webhookが発火しない

### 症状
登録済みのWebhookがエンドポイントにイベントを配信していません。Webhookダッシュボードに直近の配信が表示されない、または配信が失敗として表示されます。

### 診断
1. Settings > WebhooksのWebhookダッシュボードを確認してください。特定のWebhookをクリックすると配信履歴と失敗理由が表示されます。
2. エンドポイントがパブリックインターネットからアクセス可能か確認してください（Webhookは`localhost`やプライベートIPには配信できません）。
3. エンドポイントが10秒以内に2xxステータスコードを返しているか確認してください。タイムアウトや2xx以外のレスポンスは失敗として扱われます。
4. Webhookが正しいイベント用に登録されているか確認してください。よくある間違い: `task.created`用に登録しているのに`task.updated`イベントを期待している。

### 解決策
- **HTTPSを確認する**: Webhookには有効なSSL証明書を持つHTTPSエンドポイントが必要です。自己署名証明書は拒否されます。
- **ファイアウォールルールを確認する**: TechFlowのWebhook IPをホワイトリストに登録してください: `52.20.118.0/24`と`52.45.205.0/24`。
- **署名検証を確認する**: エンドポイントがリクエストを拒否する場合、HMAC-SHA256検証に正しいWebhookシークレットを使っているか確認してください。シークレットはWebhook登録時に一度だけ表示されます。
- **リトライ状況を確認する**: 配信に失敗すると3回リトライされます（1分後、5分後、30分後）。3回失敗すると、Webhookは「failing」としてマークされ配信が一時停止します。エンドポイントを修正した後、ダッシュボードから再有効化してください。
- **Webhookテスターで試す**: Settings > Webhooks > Testを使って、サンプルイベントをエンドポイントに送信し、レスポンスをリアルタイムで確認できます。

## クエリのパフォーマンスが遅い

### 症状
`GET /v3/projects/{id}/tasks`のようなリストエンドポイントや検索クエリのAPIレスポンスが遅い（500ms超）。遅さは断続的で、ピーク時間帯に悪化することがあります。

### 診断
1. 遅さが特定のエンドポイントに限定されているか、システム全体に及んでいるか確認してください。システム全体の遅さはデータベースの問題を示唆し、エンドポイント固有の遅さはインデックスの欠落を示唆します。
2. クエリパラメータを見直してください——ページネーションなしで大きな結果セットを取得していませんか？デフォルトの上限は25ですが、`limit=1000`を設定するとタイムアウトを引き起こすことがあります。
3. フィルタを使用しているか確認してください。大規模なプロジェクト（10,000件以上のタスク）に対するフィルタなしのリストリクエストは、本質的に遅くなります。

### 解決策
- **ページネーションを使う**: 常に妥当な`limit`（25〜100）を設定し、カーソルベースのページネーションで結果を反復処理してください。
- **フィルタを追加する**: `status`、`assignee_id`、`due_before`/`due_after`フィルタを使って結果を絞り込んでください。フィルタ済みクエリはデータベースのインデックスを使用し、フィルタなしのスキャンより10〜50倍高速です。
- **深いページネーションを避ける**: 500ページ目の結果を取得するのは遅いです。データベースが12,500行をスキップする必要があるためです。すべてのタスクを処理する必要がある場合は、バルクデータアクセス用の`GET /v3/projects/{id}/tasks/export`エンドポイントを使ってください。
- **検索エンドポイントを使う**: テキストベースの検索には、`GET /v3/tasks?title=keyword`でスキャンするより、Elasticsearchを使う`GET /v3/search?q=keyword`の方が高速です。
- **頻繁にアクセスされるデータをキャッシュする**: プロジェクトダッシュボードを表示する場合、毎回のページ読み込みでライブデータを取得する代わりに、タスク数とサマリーを30〜60秒キャッシュしてください。
- **インデックスについてサポートに連絡する**: 特定のクエリが一貫して遅い場合は、リクエストIDを添えてサポートに連絡してください。よくあるクエリパターンに対して、当社チームがデータベースインデックスを追加できます。

## 認証エラー

### 症状
APIリクエストが401 Unauthorizedまたは403 Forbiddenエラーを返します。ユーザーが予期せずログアウトされた、あるいは本来アクセスできるはずのリソースにアクセスできないと報告しています。

### 診断
1. **401エラー**: APIキーが欠落・不正な形式、または期限切れです。`X-TechFlow-Key`ヘッダーの形式を確認してください。
2. **403エラー**: APIキーは有効だが必要なスコープが不足しています。Admin Dashboard > API Keysでキーのスコープを確認してください。
3. OAuth2トークンの場合: アクセストークンが期限切れ（1時間TTL）でないか確認してください。jwt.ioでJWTをデコードし`exp`クレームを確認できます。
4. ユーザーの役割が最近変更されていないか確認してください。権限の変更は即座に反映されますが、キャッシュされたセッションは最大5分間、古い権限を保持することがあります。

### 解決策
- **期限切れトークンを更新する**: クライアントに自動トークン更新を実装してください。401を受け取ったら、リトライする前にリフレッシュトークンを使って新しいアクセストークンを取得してください。
  ```
  POST /oauth2/token
  grant_type=refresh_token
  refresh_token=<your_refresh_token>
  client_id=<your_client_id>
  ```
- **APIキーのスコープを確認する**: 各キーには特定のスコープがあります。`read`スコープのみのキーはリソースの作成や更新ができません。必要なスコープを持つ新しいキーを生成してください。
- **キーが有効か確認する**: キーはワークスペース管理者によって無効化されることがあります。Settings > API Keysでステータスを確認してください。
- **役割変更への対応**: ユーザーの役割がadminからmemberに変わると、一部のエンドポイントがアクセス不能になります。アプリケーションは403エラーを適切に処理し、ユーザーに通知する必要があります。
- **アカウント停止を確認する**: ワークスペースの請求が失敗した場合、すべてのAPIアクセスが停止されます。Settings > Billingで請求状況を確認してください。

## データ同期の遅延

### 症状
APIまたはUI経由で行った変更が、検索結果・レポート・Webhook配信にすぐには反映されません。例えば、タスクを作成しても5〜10秒間検索結果に表示されないことがあります。

### 診断
これは通常、TechFlowの結果整合性モデルによる想定内の挙動です。データパスによって遅延の程度が異なります:

| 操作 | 想定される遅延 | 理由 |
|-----------|---------------|--------|
| API応答に変更が反映される | 即座 | データベースへの直接読み取り |
| 検索インデックスの更新 | 1〜3秒 | Kafkaイベント → Elasticsearch |
| 分析ダッシュボードの更新 | 5〜10分 | バッチ集計ジョブ |
| Webhookの配信 | 1〜30秒 | キュー処理 + 配信 |
| サービス間のデータ（例: タスク内のユーザー名） | 最大5分 | 消費側サービスのキャッシュTTL |

### 解決策
- **整合性の境界を理解する**: API読み取りは強整合性があります（自分が行った書き込みは常に見えます）。検索と分析は結果整合性です。
- **リアルタイム読み取りにはAPIを使う**: 更新直後の最新状態が必要な場合、検索やキャッシュされたデータに頼らず、APIから直接読み取ってください。
- **Kafkaのコンシューマーラグを確認する**: 検索の遅延が10秒を一貫して超える場合、コンシューマーラグが発生している可能性があります。Search Serviceのヘルスダッシュボードを確認するか、サポートに連絡してください。
- **Webhookの順序**: Webhookはリソースごとに順序どおり配信されますが、異なるリソース間では順不同で届くことがあります。`event_id`と`timestamp`フィールドを使ってシステム内での順序を整合させてください。
- **キャッシュの強制更新**: Auth Serviceに限り、管理者権限で`POST /v3/auth/refresh-cache`を呼び出すことで権限キャッシュの強制更新ができます。一括での役割変更後に有用です。

## ファイルアップロードの失敗

### 症状
ファイルのアップロードがさまざまなエラーメッセージとともに失敗する、またはアップロード完了後にファイルにアクセスできません。

### 診断
1. ファイルサイズを確認してください——1ファイルあたりの上限は100MBです。
2. ファイルタイプを確認してください——実行可能ファイル（.exe、.bat、.sh、.ps1）はセキュリティ上の理由でブロックされます。
3. アップロードは成功したがファイルにアクセスできない場合、ウイルススキャンで隔離された可能性があります。`GET /v3/files/{id}`でファイルのステータスを確認してください——フラグが立っている場合、ステータスは`quarantined`になります。

### 解決策
- **大きなファイルを圧縮する**: ファイルが100MBを超える場合、アップロード前に圧縮（ZIP、GZIP）してください。
- **マルチパートアップロードを使う**: 10MBを超えるファイルには、5MBチャンクでアップロードし失敗時の再開に対応したマルチパートアップロードエンドポイント`POST /v3/files/multipart`を使ってください。
- **ストレージクォータを確認する**: ワークスペースのストレージがプランの上限（Basic 5GB、Pro 50GB、Enterprise無制限）を超えていないか確認してください。Settings > Storageで使用量を確認できます。
- **ウイルススキャンを待つ**: アップロード後、ファイルは`uploading` → `scanning` → `available`（または`quarantined`）という状態を経ます。スキャンには通常5〜15秒かかります。`GET /v3/files/{id}`をポーリングするか、`file.scanned`Webhookイベントを待ち受けてください。
