# TechFlowシステムアーキテクチャ

## 概要

TechFlowはAWS上にデプロイされたマイクロサービスアーキテクチャを採用しています。このシステムはピーク時に約50,000人の同時接続ユーザーを処理し、95パーセンタイルの平均APIレスポンスタイムは45msです。

## サービスマップ

### API Gateway（Kong）
API Gatewayは、すべてのクライアントリクエストの唯一の入り口です。SSL終端・リクエストルーティング・レート制限・APIキー検証を担当します。ゲートウェイはAWS Application Load Balancer配下の4インスタンスで稼働し、CPU使用率（目標: 60%）に基づいて4〜12インスタンスの間でオートスケーリングします。

### Auth Service
認証・認可を担当します。ユーザーセッション・APIキー検証・OAuth2フロー・権限チェックを管理します。Python（FastAPI）で構築され、ユーザーデータにはPostgreSQL、セッションキャッシュにはRedisを使用します。セッショントークンはJWTベースで、有効期限は1時間です。このサービスは、owner・admin・member・guestの4つの役割を持つロールベースアクセス制御（RBAC）モデルで権限を検証します。

### Project Service
プロジェクト・タスク・ラベル・ワークフローのコアビジネスロジックです。最大のサービス（約40,000行）で、プロジェクト管理のすべてのCRUD操作を処理します。Python（Django）とPostgreSQLで構築されています。並行リクエストを効率的に処理するため、データベース接続プーリング（PgBouncer、最大200接続）を使用しています。複雑なクエリ（レポート・分析）は、書き込み性能への影響を避けるため読み取りレプリカにルーティングされます。

### Notification Service
すべてのアウトバウンド通知を管理します: メール（AWS SES経由）、アプリ内通知（WebSocket経由）、プッシュ通知（Firebase Cloud Messaging経由）、Webhook配信。Node.jsで構築され、通知処理をメインのリクエストフローから切り離すためRedisベースのキューを使用します。Webhook配信の失敗は指数バックオフでリトライされます。このサービスは1日あたり約200万件の通知を処理します。

### Search Service
プロジェクト・タスク・コメント全体の全文検索を提供します。コードスニペット検索用のカスタムアナライザーを備えたElasticsearch上に構築されています。インデックスはKafkaイベント経由で非同期に更新されます。検索結果は、テキストの関連性・新しさ・ユーザーの活動シグナルを組み合わせてランク付けされます。古くなったエントリを整理するため、インデックスは毎晩再構築されます。

### File Service
ファイルのアップロード・保存・取得を担当します。ファイルはAWS S3に保存され、配信にはCloudFront CDNを使用します。100MBまでのファイルに対応しています。画像のサムネイルとドキュメントのプレビューレンダリングを生成します。ファイルが利用可能になる前に、ClamAVによるウイルススキャンが非同期で実行されます。ストレージのクォータはワークスペースごとに適用されます: 5GB（Basic）、50GB（Pro）、無制限（Enterprise）。

## データベースアーキテクチャ

### PostgreSQL（プライマリデータベース）
- **バージョン**: AWS RDS上のPostgreSQL 15
- **構成**: 自動フェイルオーバー付きのマルチAZデプロイ
- **プライマリインスタンス**: db.r6g.2xlarge（8 vCPU、64GB RAM）
- **読み取りレプリカ**: 分析クエリとレポートダッシュボードに使用
- **バックアップ**: 30日間保持される自動日次スナップショット、ポイントインタイムリカバリ有効
- **テーブル**: 6つのスキーマ（public、auth、projects、billing、audit、analytics）にまたがる47テーブル

### Redis（キャッシュ、セッション）
- **バージョン**: AWS ElastiCache上のRedis 7
- **クラスター**: 自動フェイルオーバー付きの3ノードクラスター
- **用途**: セッションストレージ（TTL: 1時間）、APIレスポンスキャッシュ（TTL: 5分）、レート制限カウンター、リアルタイムプレゼンス追跡
- **メモリ**: ノードあたり32GB、退避ポリシー: volatile-lru

### Elasticsearch（検索）
- **バージョン**: AWS上のOpenSearch 2.11
- **クラスター**: データノード3台 + 専用マスターノード2台
- **インデックス**: projects、tasks、comments、files（メタデータのみ）
- **リフレッシュ間隔**: 1秒（ニアリアルタイム検索）

## イベント駆動アーキテクチャ

サービス同士はApache Kafkaを介して非同期に通信します。これによりサービス間が疎結合になり、部分的な障害時でも信頼性の高いイベント処理が可能になります。

### Kafka構成
- **クラスター**: AWS MSK上のブローカー3台
- **レプリケーション係数**: 3（すべてのメッセージが全ブローカーに保存される）
- **保持期間**: すべてのトピックで7日間

### 主要トピック
- `project.events` — プロジェクトの作成・更新・アーカイブ・復元。消費元: Search Service、Notification Service、Analytics。
- `task.events` — タスクの作成・更新・ステータス変更・割り当て・コメント。消費元: Search Service、Notification Service、Analytics。最も流量の多いトピック（約50万イベント/日）。
- `user.events` — ユーザーの登録・プロフィール更新・役割変更・無効化。消費元: Auth Service（キャッシュ無効化）、Notification Service。
- `file.events` — ファイルのアップロード・スキャン・削除。消費元: File Service（サムネイル生成）、Search Service（メタデータインデックス化）。
- `billing.events` — サブスクリプションの作成・アップグレード・ダウングレード・支払い失敗。消費元: Notification Service、Auth Service（フィーチャーフラグ更新）。

### イベントスキーマ
すべてのイベントは標準的なエンベロープ形式に従います:
```json
{
  "event_id": "evt_abc123",
  "event_type": "task.updated",
  "timestamp": "2024-01-15T10:30:00Z",
  "actor_id": "usr_xyz789",
  "workspace_id": "ws_def456",
  "payload": { ... }
}
```

## デプロイトポロジー

すべてのサービスは以下の構成でAWS ECS（Fargate）上で稼働しています:
- **リージョン**: us-east-1（プライマリ）、eu-west-1（災害復旧）
- **ネットワーキング**: パブリックサブネット（ロードバランサー）、プライベートサブネット（サービス・データベース）を持つVPC
- **DNS**: ヘルスチェックベースのフェイルオーバー付きRoute 53
- **CDN**: 静的アセットとファイルダウンロード用のCloudFront
- **シークレット**: APIキー・データベース認証情報・暗号化キー用のAWS Secrets Manager
